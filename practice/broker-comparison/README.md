# Отчет: RabbitMQ vs Redis

## 1. Условия теста

- Среда: Docker, single instance RabbitMQ и Redis
- Параметры:
  - размеры сообщения: 128B, 1KB, 10KB, 100KB
  - интенсивность: 1000, 5000, 10000 msg/sec
  - сообщений на прогон: 5000
- Статус прогона: завершен успешно (`Done. Files saved: results/results.json and results/results.csv`)

## 3. Базовое сравнение

- Кто показал выше throughput:
  - На низком потоке (`1000`) Redis быстрее почти для всех размеров.
  - На `5000` и `10000` RabbitMQ чаще быстрее, особенно на крупных сообщениях.
- Где меньше latency:
  - Для `1000` и небольших сообщений Redis имеет ниже p95.
  - На высоком потоке и крупных сообщениях RabbitMQ имеет заметно ниже p95.
- Были ли ошибки:
  - Ошибок нет (`errors = 0` во всех 24 прогонах).

## 4. Влияние размера сообщения

- Как меняется throughput при росте payload:
  - У Redis при росте payload throughput падает и держится в районе ~260-277 msg/s на 100KB.
  - У RabbitMQ при 100KB и высокой целевой интенсивности throughput остается высоким (до ~1938 msg/s).
- Кто быстрее деградирует:
  - В этой серии тестов быстрее деградирует Redis при переходе к 100KB.

## 5. Влияние интенсивности

- На каком rate начинает расти backlog:
  - Backlog не зафиксирован (`queue_left = 0` везде).
- На каком rate растет p95 latency:
  - Явного роста p95 от увеличения rate нет; чаще наоборот p95 снижается на RabbitMQ при более высокой целевой интенсивности.
- Где появляются ошибки:
  - Ошибок не появилось ни в RabbitMQ, ни в Redis.

## 6. Точка деградации single instance

- RabbitMQ:
  - Точка отказа/деградации в текущем диапазоне (`до 10000 msg/sec`, `до 100KB`) не достигнута.
- Redis:
  - Явной точки отказа нет, но видна деградация пропускной способности на 100KB и высоких rate.

## 7. Вывод

- Если сценарий — небольшой поток и маленькие сообщения, Redis показывает хорошие latency/throughput.
- Если нужен более высокий throughput под нагрузкой и особенно на больших сообщениях, RabbitMQ в этом эксперименте выглядит устойчивее.
